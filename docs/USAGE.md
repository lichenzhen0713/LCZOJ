## 一、普通用户

### 1. 注册 / 登录 / 找回密码

- 首次打开网站，右上角「登录 / 注册」；管理员账号为 **admin**，**初始密码在安装后的首次启动时随机生成**——启动日志会打印一次，同时写入数据目录的 `admin-password.txt`（可在服务器上查看；登录后请立即在「系统设置」中修改密码）。
- **注册**：填写用户名（2–20 位字母 / 数字 / 下划线 / 中文）、邮箱、密码（至少 10 位，且含字母 / 数字 / 符号中至少两类）。
  - 若管理员**关闭**了「邮箱验证」（默认）：提交后账号立即创建并自动登录。
  - 若管理员**开启**了「邮箱验证」：提交注册后**账号还不会创建**，服务端只留下一条「待验证注册」记录；请填写邮箱收到的 **6 位验证码**完成验证，**验证通过后账号才会真正创建**（页面会提示「账号已创建，请登录」）。验证码 10 分钟内有效、最多可试 5 次，可点「重新发送验证码」（重发后旧验证码立即失效）。
  - **邮件发不出去时**（未配置 SMTP / 认证失败 / 连不上邮件服务器）页面会提示「验证码邮件发送失败，请联系管理员」，验证码只写入服务器日志，**不会显示在页面上**；此时可稍后点「重新发送验证码」，或联系管理员配置邮件服务。**在完成验证前不会产生任何账号**，不会留下半成品。
  - 关掉页面后想继续验证：打开 **`#/verify`**，输入注册邮箱获取/重发验证码并完成验证（同样需要邮件服务可用）。
- **登录**：支持**用户名或注册邮箱**登录。
- **老账号（v2.5.0 之前的未验证账号）**：不会被删除或迁移；站点开启邮箱验证时仍须先完成邮箱验证才能登录（可用 `#/verify` 补验证），站点**关闭**邮箱验证时可直接登录，不会被锁死。
- **忘记密码**：登录页「忘记密码」→ 输入注册邮箱 → 获取验证码（验证码只发到邮箱，10 分钟内有效）→ 设置新密码。

### 2. 页面导航与个人中心

> **系统设置**：侧边栏「系统设置」（#/settings）已从管理后台独立出来，并按内容分成「网站外观 / 邮箱与验证 / 功能设置 / 评测设置 / 页面与版权 / 版本更新」六块，点顶部分类只看一块（地址如 #/settings/appearance）；「清理多余数据」「批量生成用户」「批量删除」三个分类直接进入对应页面。
>
> **页面宽度**：站长可在「管理后台 → 网站外观 → 页面宽度」设置全站宽度，以及为每个页面单独设定宽度（留空=使用内置默认值）。博客文章与题解详情默认 860px 便于阅读，其余页面跟随全站宽度。

侧边栏导航（登录后可见的入口按权限与功能开关变化）：

| 入口 | 说明 |
| --- | --- |
| 首页 | 站点概览、公告、每日打卡、最新题目与提交动态 |
| 题库 | 题目列表与筛选 |
| 比赛 | 比赛列表、报名与比赛页 |
| 排行榜 | 用户积分 / 等级分排行 |
| 题解与专栏 | 全站题解与专栏文章 |
| 讨论 | 讨论区各板块 |
| 提交记录 | 全站提交（默认只看自己的） |
| 社区管理 | 拥有管理权限时可见（权限操作记录） |
| 管理后台 / 系统设置 | 拥有对应权限时可见 |

页脚公开页（均由管理员在「系统设置」中编辑）：**帮助中心、用户协议、联系我们、关于网站、社区规则、反馈与举报**。

**个人中心**（点击右上角头像）含 4 个 Tab：

- **主页**：等级分变化曲线、个人简介、积分情况、最近提交；
- **练习**：**尝试过的题目**（含未通过的，标签显示尝试次数）与**已通过的题目**，右侧为各难度通过数量统计（8 个难度档位，未通过显示 0）；
- **专栏**：自己发布的题解与专栏文章，可编辑 / 删除；
- **收藏**：收藏的题目 / 讨论 / 比赛。

**编辑资料**（头像 → 编辑资料）：

- 修改**用户名**（每年 3 次机会，管理员不受限制）、**头像**（本地上传 ≤ 500 KB 或填写图片 URL）、**简介**（支持 Markdown 与数学公式）；
  - 新用户默认带一张**自动生成的像素画头像**（由用户名决定，同一用户名永远得到同一张图），可随时换成自己的图片；清除已上传的头像后会回到这张默认头像；
- 修改**邮箱**：填写新邮箱 → 「获取验证码」（验证码发往新邮箱）→ 输入验证码 → 「验证并更换邮箱」；
- **修改密码**：输入当前密码与两次新密码。

### 3. 题库与题目页

1. **题库列表**：支持**搜索**（题名 / 标签）与**难度、算法标签、来源标签**筛选（标签支持多选组合）。
2. **题目页**包含：题面区块（题目背景 / 题目描述 / 输入格式 / 输出格式 / 样例 / 提示，均按实际填写内容显示）、题目信息卡（难度、时间与内存限制、通过数 / 提交数、标签与来源）、提交卡片、以及题解区与讨论区入口。
3. **题面为 Markdown + LaTeX**：数学公式自动渲染；样例输入 / 输出与代码块均带「复制」按钮。
4. **题目信息卡**中会标注该题是否为 **Special Judge**、**提交答案题**，以及是否开启 **O2 优化**。

### 4. 提交代码

提交卡片顶部可在 **提交代码** 与 **提交代码文件** 两种模式之间切换（会记住上次选择）。

1. 在 **语言** 下拉中选择语言；第一项为 **自动识别语言**（提交时才按代码内容判断实际语言，因此编写过程中不会中途改语言）；
2. 在代码框中编写或粘贴代码；标题栏显示当前语言与字符数（选择「自动识别语言」时只显示字符数）；
3. 可用 **提交级 O2 开关** 单独覆盖题目的默认设置（仅影响 C/C++ 编译参数）；
4. 点「提交评测」后自动跳转到评测结果页。

> **语言默认值**：默认选中**上次提交时实际使用的语言**（「自动识别语言」也会被记住）；仅在下拉中选择而不提交，不会改变下次的默认值。

### 5. 提交代码文件

适合直接把本地源文件提交：

- 切到「提交代码文件」模式后，点击虚线区域选择文件，或**把文件拖到虚线区域 / 整个提交卡片上**；
- 支持单文件 ≤ 64 KB；**按文件扩展名自动识别语言**（也可在语言下拉中手动指定）；
- **文件内容直接提交，不会载入代码框**；提交前会显示文件名、大小与识别出的语言，可清除重选。

### 6. 提交答案题

- 此类题目的提交卡片标题为「**提交答案**」，界面为文件上传而非代码框；
- **单测试点**：上传一个答案文件；**多测试点**：打包为 **ZIP**（内含 `1.out`、`2.out` …，也支持 `.ans` / `.txt`）；
- 未选择文件时「提交答案」按钮不可用；上传区支持点击选择与拖拽，图标与配色跟随站点主题；
- 评测时按测试点与该题的标准答案比较（题目开启 SPJ 时由 checker 判定）。

### 7. 评测结果与提交记录

- 判题状态依次为：等待评测 → 评测中 → 完成；结果（verdict）包括：

  | 结果 | 含义 |
  | --- | --- |
  | 通过（AC） | 全部测试点正确 |
  | 答案错误（WA） | 输出与标准答案不一致 |
  | 超时（TLE） | 超出该测试点实际生效的时间限制（测试点级优先，否则题目级） |
  | 内存超限（MLE） | 超出该测试点实际生效的内存限制（同上） |
  | 运行错误（RE） | 程序非正常退出 |
  | `Compile Error`（编译错误，缩写 CE） | 编译失败，详情页显示编译输出 |
  | 系统错误（SE） | 评测机或 checker 异常 |

- 输出比较**忽略行末空格与末尾换行**；开启 SPJ 的题目由 checker 判定，支持部分分；
- **提交详情**按测试点展示结果、耗时、内存与所属子任务；
- **代码可见性**：通过（AC）之后可查看他人代码，未通过前仅本人与管理员可见；
- **提交记录列表**默认只看自己的，可按**用户名 / 题目 ID** 筛选；比赛中的提交会标注「赛时提交」。

### 8. 题解与专栏

- 入口在侧边栏「题解与专栏」，支持**按分类筛选**（全部 / 未分类 / 题解 / 科技·工程 / 算法·理论 / 生活·游记 / 学习·文化课 / 休闲·娱乐；内部 key 分别为 `uncategorized` / `solution` / `tech` / `algorithm` / `life` / `study` / `entertainment`）；
- 每篇文章支持**点赞**与**评论**（评论支持 Markdown 与公式）；
- **写题解**：从题目页进入，自动关联该题；**写文章**：从「题解与专栏」页进入并选择分类；
- 编辑器为**左右分栏**：左侧 Markdown 源码、右侧实时预览；可**保存草稿**或**提交审核**；
- 文章 / 题解需管理员**审核通过**后公开；被驳回可修改后重新提交；草稿仅自己可见。

### 9. 讨论区

- 板块：**学术版 / 灌水区 / 站务版 / 题目讨论**；题目页底部可直接进入该题的讨论；
- 发帖与回复支持 Markdown、数学公式与 **@提及**（被提及者会收到通知）；
- 管理员可置顶 / 删除 / 关闭回复；发言受限的用户（棕名封禁期间）无法发帖或回复。

### 10. 比赛

三种赛制：

| 赛制 | 排名方式 | 题目状态显示 |
| --- | --- | --- |
| ACM | 解题数 + 罚时 | ✓ 通过 / ✗ 错误 |
| IOI | 每测试点即时给分 | 得分（取本场最高分） |
| OI | 赛中隐藏成绩，赛后公布 | 已提交 / 未提交 |

- **所有比赛都需要报名**：在比赛页点「报名比赛」后即可查看题目并参赛（Rated 比赛可选择是否计入等级分）；
- 右侧「比赛信息」卡片中，**「我的报名」与「是否计算等级分」分为两块分别展示**：前者显示「已报名 / 未报名 / 报名已截止」，后者显示本场你选择的是「计算等级分」「不计等级分」（Unrated 比赛显示「Unrated（本场不计等级分）」）；
- 赛时提交在比赛页面进行，提交记录标注「赛时提交」；
- 排行榜每页 30 名、支持翻页；**Rated** 比赛结束后由管理员「结算等级分」，随后可在个人中心看到等级分变化。

### 11. 积分 / 等级分 / 每日打卡 / 排行榜

- **积分**：由「基础分 / 练习分 / 比赛分 / 社区分」四维推导（**不落库**）：刷题（练习分）、参加比赛（比赛分）、社区贡献（**题解 / 专栏、讨论主题帖、讨论回复、题解与专栏被赞**）都会增长；用户颜色随积分变化。
  v2.6.0 起**比赛降权、社区提权**：比赛分系数 15%（历史 100%）、第一名加成 1.8（历史 3.0），社区分系数 160%、单篇题解 / 专栏基础权重 8（历史 4），并新增发帖 / 回复 / 被赞计分；这些权重是 `src/users.js` 里的**代码常量**（`POINTS_WEIGHTS`，见 [CUSTOMIZATION.md](CUSTOMIZATION.md) 第七节），改完重启服务即全站生效 —— 积分是推导值（`users` 表没有 points 列），不存在需要清零或重算的落库字段；
- **每日打卡**：首页打卡卡片，每日 **00:00（服务器本地时间）** 重置，可累计连续天数；
- **全站积分结算**：积分始终是**四维推导值**（`users` 表没有 points 列），「**系统设置 → 功能设置 → 全站积分结算**」可以把**全站用户的四维积分一次性重算并落库成快照**（`points_settlement` 表），供排行榜 / 个人中心快速读取，并留下可追溯的历史。三种模式：**实时**（**默认**，显示始终取实时计算值，后台每 60 秒也写一次快照但只作历史）/ **定时自动**（距上次结算超过设定间隔才执行一次，间隔在界面上按**小时 / 天**录入，范围 **1 小时 ~ 30 天**，留空默认 **6 小时**）/ **手动结算**（点同页的「**立即结算全站积分**」按钮执行一次）。**读取规则**：手动 / 定时模式下，排行榜、个人中心与用户名颜色**优先读快照**（某用户尚无快照行时回退实时计算，不会空白或显示 0 分）；**实时**模式下**始终实时计算**，快照只作历史。设置区下方以信息芯片显示当前模式说明与上次结算时间 / 耗时 / 覆盖人数 / 下次预计（时间口径为**小时 / 天**）。结算只写积分快照，**不计算等级分**、不动 `rating_history`；
- **等级分**：仅 Rated 比赛结算后产生，个人中心展示变化曲线；
- **排行榜**：按积分 / 等级分排序查看全站用户。

### 12. 私信与通知

- **私信**：顶栏信封图标进入，一对一会话列表 + 未读红点；站长可在「系统设置 → 功能设置」中整体关闭私信（关闭后入口隐藏、直接访问 `#/messages` 会被拦下并提示「私信功能已关闭」，数据保留）；
- **通知**：顶栏铃铛显示未读数，涵盖被 @、被回复、审核结果、系统通知等，点击进入通知中心。

### 13. 收藏、反馈与举报

## 二、管理员：题目数据配置（重点）

> 入口：侧边栏「管理后台」→ **题目管理**。新建题目保存后进入编辑页；页面顶部按来源显示「返回题库」或「返回管理后台」。

### 1. 题目编辑器字段

**基本信息**

| 字段 | 说明 |
| --- | --- |
| 标题（必填） | 题目标题 |
| 时间限制 / 内存限制 | 单位毫秒 / MB，评测按此限制判定 TLE / MLE |
| 开启 O2 优化 | 题目级默认值，用户提交时可单独覆盖（仅影响 C/C++） |
| 题目类型 | 共 5 种：**普通题** / **提交答案** / **交互题 · IO** / **交互题 · 函数式** / **通信题（两程序）**（题目页「特性」徽章与这里的文案一致；通信题见第 15 节）；选交互题后出现「交互题配置」卡片（交互器、grader、头文件、交互说明），详见 [INTERACTIVE.md](INTERACTIVE.md) |
| 使用 Special Judge（SPJ） | 使用自定义 checker 判定答案；**五种题目类型共用顶部这一个开关**，勾选后紧接着展开 checker 源码编辑 / 上传（同一份 `checker.cpp`） |
| 提交答案 | 已并入「题目类型」下拉：类型选「提交答案」即用户上传答案文件而不是编写代码 |
| 难度 | 8 个档位（暂未评级 / 入门 … NOI+） |
| 算法标签 / 来源标签 | 逗号分隔，用于题库筛选 |
| 公开可见 | 关闭后不在题库列表展示（仍可通过直链或比赛访问） |
| 显示分数（OI） | 提交记录与榜单是否显示分数 |
| 关闭题解提交 | 关闭该题的题解提交入口 |

**题面内容**：题目背景、题目描述、输入格式、输出格式、样例（可增删多组）、提示。均支持 Markdown 与 LaTeX；留空的区块不会在题目页显示。

**保存后**：编辑页还提供「导出题目」「迁移题号」等操作（见后文）。

### 2. 测试数据基本概念

每个测试点由一对文件组成：

- **输入文件** `N.in`：评测时作为标准输入喂给用户程序；
- **输出文件** `N.out`（或 `N.ans`）：标准答案。

评测时逐测试点运行用户程序，比较其输出与标准答案（忽略行末空格与末尾换行），汇总为题目得分（满分 100）。

### 3. 逐测试点编辑

在编辑页「测试数据」卡片中：

- 每个测试点一行，含**输入 (.in)** 与**输出 (.out)** 两个输入框；
- 可点「选择文件」把本机文件内容读入对应输入框（大文件同样可读入）；
- 每个测试点可设置**子任务编号**；
- 每个测试点还可单独设置**时限 (ms)** 与**内存 (MB)**（**测试点级限制**）：填写后该测试点按此限额判定，**留空 = 继承题目基本信息里的全局限额**（输入框占位符会显示继承到的值，如「继承 1000」）；
- 「+ 添加测试点」新增（新行默认留空 = 继承），行内「删除」移除；
- 修改后点「**保存测试数据**」生效（不会影响已有的 checker.cpp）。

> **测试点级限制的口径**：**点级优先，未设置才用题目级**；点级限额**同时**约束该测试点的 TLE 与 MLE。
> 超限提示里给出的是**实际生效**的限额，例如「运行超时（实测 3200 ms > 该测试点时限 2000 ms）」「内存超限（峰值 600 MB > 该测试点限制 512 MB）」。
> 子任务分数、计分方式、SPJ / 交互题配置都不受点级限额影响；旧题目（没有点级设置）完全按题目全局限额判定。
> **题目页显示**：各测试点的**实际生效限额**（点级优先、留空继承题目级）**一致**时，题目信息里显示单个值（如「时间限制 1000 ms」）；
> **不一致**时显示**区间**（如「时间限制 500 ms ~ 2000 ms」「内存限制 256 MB ~ 512 MB」），方便选手一眼看出各点差别。
> 题目**导出 → 导入**（JSON / ZIP 清单）会带上点级限额；上传测试数据 ZIP 的「合并」模式会沿用同编号测试点原有的限额设置。

### 4. ZIP 测试数据包上传：覆盖 / 合并

1. 将测试数据打包为 **ZIP**：`1.in / 1.out`、`2.in / 2.out` …（也支持 `.ans`；可含子目录，文件名中含数字即可识别，如 `data/01.in`）；
2. 点「上传 ZIP 测试数据包」并选择文件；
3. 上传前用「**覆盖当前数据**」开关选择处理方式：

   | 模式 | 行为 |
   | --- | --- |
   | 勾选（默认，覆盖） | 整体替换，只保留新包中的测试点 |
   | 取消勾选（合并） | 同编号测试点被新包覆盖、新编号追加、其余保留（如现有 1~3，新包含 2、4 → 结果 1、2(新)、3、4） |

   合并时若新包未提供子任务分数与计分方式，则沿用现有配置。

4. **SPJ 题目**：把 `checker.cpp` 一并放进 ZIP（评测机已内置 `testlib.h`，无需随包上传），上传后自动编译生效；**SPJ 题的数据包必须包含 `checker.cpp`，否则会被拒绝**。也可在「checker.cpp 内容」中直接粘贴 / 载入本地文件后保存。

### 5. 子任务分组与分数

- 给每个测试点填写**子任务编号**（1、2、3 …），编号相同的测试点属于同一子任务；
- 在「**子任务分数**」中按顺序填写各子任务满分，逗号分隔（如 `30,70`，合计 100）；留空则平均分配；
- 子任务内的测试点**捆绑评测**，是否得分取决于下节的计分方式。

### 6. 子任务计分方式（sum / min / max / bundle）

在「**子任务计分方式**」中按顺序填写（逗号分隔，与子任务编号一一对应）：

| 方式 | 含义 |
| --- | --- |
| `sum` 加和 | 各测试点均分子任务满分，按通过比例累加（全对得满分） |
| `min` 最小值 | 子任务得分 = 满分 × 各测试点部分分比例的**最小值**（最差测试点决定整组） |
| `max` 最大值 | 子任务得分 = 满分 × 各测试点部分分比例的**最大值**（最好测试点即可拿满） |
| `bundle` 捆绑 | 子任务内**全部**测试点通过才得整组分数，否则 0 分 |

> 部分分比例：普通评测 AC = 1、否则 0；Special Judge 输出 0~1（或 1~100）数值时按比例计部分分，四种方式均适用。
> **只有一个子任务时默认按 `sum` 计分**；完全不填写则按 `bundle`（兼容旧题目）。

### 7. 大数据测试包（不预览，正常评测）

- 单个测试文件超过 **16 KB** 时**不在编辑页预览**（避免浏览器卡死），只显示「数据过大」提示与文件大小；
- 预览截断**不影响评测**：判题机始终读取服务器上的**完整**数据文件，几十 MB 的数据包可正常评测；
- 对这类测试点直接点「保存测试数据」时，系统**自动沿用服务器上的完整数据**（仅当你重新选择文件或修改文本框后才会替换）；
- 删除某个测试点行后，其余测试点按原始文件编号保留对应数据，不会错位。

### 8. Special Judge（SPJ）

答案不唯一（如输出任意可行解）时使用：

1. 在题目编辑器**顶部公共设置区**勾选「**使用 Special Judge（SPJ）**」（五种题目类型共用这一个开关，勾选后其下方即展开 checker 编辑 / 上传区）；
2. 提供 checker 的两种方式（任选其一）：
   - 测试数据 ZIP 包内放入 `checker.cpp`；
   - 顶部开关下方的「checker.cpp 内容」直接粘贴，或点「选择 checker.cpp 文件」载入后保存；
3. 评测时自动编译（`g++ -fno-asm -std=c++14 -O2`），每个测试点按 Testlib 约定运行 `checker <in> <ouf> <ans>`：

   > **checker 只编译一次**：编译产物按「checker 源码 + testlib.h + 编译参数」的内容哈希缓存在 `data/spj_cache/`，
   > 之后每次评测都直接复用，不再重复编译（checker 改动后自动重新编译；缓存超过 30 个或 30 天未使用会被淘汰）。

   | 退出码 / 输出 | 判定 |
   | --- | --- |
   | `0` | AC；若标准输出含 0~1（或 1~100）数值，则按比例计**部分分** |
   | `1` | WA |
   | `2` | 格式错误（按 WA 处理） |
   | `3` | checker 自身异常（判 SE） |

   常用写法：`quitf(_ok, ...)` 通过、`quitf(_wa, ...)` 错误、`quitp(0.5, ...)` 部分分。
4. **交互题开 SPJ 时 `ouf` 从哪来**：交互题 · IO 由**交互器把选手的最终答案写入 `argv[2]` 指定的文件**，交互结束后用它作为 `ouf`；交互题 · 函数式则用 grader 的**标准输出**作为 `ouf`。写法见 [INTERACTIVE.md](INTERACTIVE.md)。

### 9. O2 优化与提交答案题

- **O2 优化**：题目可默认开启 / 关闭（仅影响 C/C++ 的 `-O2`）；用户提交时可单独选择，提交级设置覆盖题目默认值；
- **提交答案题**：题目设置勾选后，用户提交界面变为**文件上传**（语言固定为「提交答案」）；该开关在新建与编辑题目时都可随时切换；评测按测试点与标准答案比较（勾选 SPJ 时由 checker 判定）。

### 10. 题目批量导出

> 入口：**题目管理**页表格左侧勾选框 + 页面底部按钮；单题导出也可在题目编辑页使用。

| 操作 | 说明 |
| --- | --- |
| **导出所选** | 勾选任意题目（表头可全选）后导出为一个 ZIP；按钮显示已选数量，未选中时禁用 |
| **导出当前筛选结果** | 按当前搜索 / 标签 / 来源 / 难度导出**全部**匹配题目（不受分页限制，单次最多 500 题） |
| **导出全部题目** | 整库打包为一个 ZIP |
| **导出清单 JSON** | 只导出题目清单（测试数据内联），便于脚本处理或仅备份题面 |

导出包（ZIP）结构：

| 内容 | 说明 |
| --- | --- |
| `import.json` | 题目清单数组，测试数据与子任务分数内联，每题的 `dir` 指向自己的数据目录 |
| `data/<题号>/*.in`、`*.out` | 各题测试数据文件（便于人工查看） |
| `data/<题号>/checker.cpp` | SPJ 题目的 checker |
| `README.txt` | 包内说明（题目数、测试点数、导出时间） |

导出包**可直接在导入页整体还原**，用于题库备份或跨站点迁移。

### 11. 题目批量导入

> 入口：**题目管理**页面右上角的「**导入题目**」按钮（单题 JSON 与整包 ZIP 使用同一个入口）。

**支持的格式**

- 本站导出的 ZIP（含 `import.json` 与 `data/<题号>/`）；
- 自定义 ZIP：根目录（或任意目录）放 `import.json` / `problems.json` 清单，每题用 `"dir": "p1"` 指定数据目录，目录内放 `1.in`、`1.out`… 与可选 `checker.cpp`；
- 纯 JSON：单个题目对象或题目数组，可**直接粘贴**在页面文本框，也可上传 `.json` 文件。

**导入预检**：选择文件或粘贴 JSON 后，页面先做一次**只解析、不写入**的预检，列出每道题的标题、测试点数、类型（普通题 / SPJ / 提交答案题 / 隐藏）以及是否为**同名题目**（附已存在的题号），并汇总「共 N 题（新题 / 同名 / 异常）、测试点合计」。

**同名冲突策略**（下拉选择）：

| 策略 | 行为 |
| --- | --- |
| 跳过（默认） | 题库中已存在同标题题目时跳过；重复导入同一份包不会产生重复题 |
| 覆盖 | 更新该题题面并覆盖其测试数据（题号不变） |
| 允许重复 | 同标题再新建一道题目 |

**导入结果**分三部分展示：导入成功（含「新建 / 覆盖」标记与测试点数）、跳过同名题目（附题号）、失败条目及原因；单条失败不影响其它题目。

> 单次最多导入 **200** 道题目、每题最多 **200** 个测试点。

### 12. 题号迁移

题目编辑页提供「**迁移题号**」：把题目整体搬到新的题号下，**同时迁移**该题的提交记录、题解、讨论、收藏、比赛关联（数据库）与测试数据、附件（磁盘）。迁移在事务中执行，失败会自动回滚。

### 13. 交互题（IO 交互 / 函数式交互）

> 完整写法、退出码对照与常见问题见 [INTERACTIVE.md](INTERACTIVE.md)；这里只讲「怎么建一道交互题」。

**建题四步**

1. **选类型**：题目编辑器 →「基本信息 → 题目类型」选 `交互题 · IO` 或 `交互题 · 函数式`（下拉共 5 项：传统题 / 提交答案 / 交互题 · IO / 交互题 · 函数式 / 通信题（两程序），最后一项见第 15 节）；选好后页面出现「交互题配置」卡片；
2. **填交互题配置**：
   - **交互器源码（interactor.cpp）**：交互题 · IO 必填。直接粘贴，或点「选择 interactor.cpp 文件」载入本地文件；评测机以 `interactor <测试输入文件> <交互器输出文件>` 启动它——从 `argv[1]` 读取该测试点的 `.in` 作为隐藏数据，通过标准输入输出与选手对话，用退出码给结论（`0`=AC、`1`/`4`=WA、`2`=WA（格式错误）、`3`=判题失败、`7`=按对错计分）；开启 SPJ 时还要把选手的最终答案写入 `argv[2]`；
   - **grader 源码（grader.cpp）**：交互题 · 函数式必填（仅该类型显示）。grader 自带 `main()`，评测时与选手提交一起编译链接，退出码 `0` 判 AC；开启 SPJ 时 grader 的标准输出作为 `ouf` 交给 checker；
   - **头文件**：点「添加头文件」逐个添加（名称如 `problem.h` + 内容 / 上传）；函数式交互题的接口声明就写在这里，grader 与选手都能 `#include` 它；
   - **交互说明**：Markdown，会作为一个「交互说明」区块展示在题目页，写清提问格式 / 函数签名 / 调用约定与限制；
   - **使用 Special Judge（SPJ）**：不在交互题卡片里，而是在题目编辑器**顶部的公共设置区**统一勾选（五种题目类型共用）；勾选后由 checker 判定该题：交互题 · IO 由交互器写入 `argv[2]` 的最终答案作为 `ouf`，交互题 · 函数式由 grader 的标准输出作为 `ouf`，运行 `checker <in> <ouf> <ans>`；
3. **保存题目信息**：类型、SPJ 勾选、交互说明与上述源码一并保存（写入 `data/testdata/<题号>/`）；清空某个文本框再保存即删除对应文件，把头文件行删掉再保存即删除该头文件；
4. **配测试数据**：照常上传 / 填写 `1.in / 1.out`…；交互题里 `.in` 就是交互器（或 grader）要读的隐藏数据，`.out` 可以不填（开 SPJ 时 checker 需要标准答案就照常填）。

**评测与计分**

- 交互题每个测试点由交互器 / grader 判定 AC 或 WA，按普通题的**子任务分数**汇总（`sum` / `min` / `max` / `bundle` 均适用）；
- 勾选 SPJ 后改由 checker 判定（可给部分分：`quitp(比例, ...)`），判定与普通 SPJ 题完全一致；
- 交互器与 grader 的消息会显示在**提交详情 →「交互器消息」**与测试点悬停提示中，方便排查；
- 交互题 · 函数式**仅支持 C / C++**：选手提交其它语言会直接给出提示，不会逐点重试。

**种子演示题**：全新安装的题库里自带 **6 道演示题**——「A+B Problem」（普通评测）、「SPJ 测试题」（Special Judge）、「提交答案测试题」（提交答案）、「IO 交互测试题（猜数字）」、「函数式交互测试题（不许偷看）」（交互题 · IO / 函数式）与「通信题演示：两程序合作求最大子段和」（**通信题**，见第 15 节），可直接查看题面、交互说明与后台配置作为模板；已有站点升级时按 slug **幂等补齐**缺失的演示题，不重复插入、不覆盖已有题目（若老站点里已有「交互题 + Special Judge」演示题，则继续保留并随版本刷新其交互器 / checker）。

### 14. 函数式交互题（旧称「通信题」）

> **提示（v2.7.8 起）**：站内现在有了**独立的「通信题」类型**（`problem_type = 'communication'`，需要**两个选手程序**合作完成任务），见下一节 [15. 通信题](#15-通信题两个选手程序合作)。本节讲的 `interactive_func` 是「**函数式交互题**」——选手只实现题目给的头文件里的函数、评测时与 grader 一起编译链接；它与新的通信题是**两个不同的类型、两套不同的评测实现**，不要混用。

> **完整写法、退出码对照与常见问题见 [INTERACTIVE.md](INTERACTIVE.md)**；本节只讲「函数式交互题是什么、要准备哪些文件、选手怎么写」。

**为什么这里叫「函数式交互题」**：它历史上被本站叫成「通信题」（因为「题目与选手之间有通信约定」），但**与第 15 节的通信题不是一回事**：函数式交互题只有**一个**选手程序（只实现头文件里的函数），没有「两个程序互相传递数据」这层结构。

**这类题在干什么**：题目提供一份**评测器（grader.cpp）**与一份**头文件（如 problem.h）**，选手只实现头文件里声明的若干函数；评测时把 grader 与选手代码**一起编译链接**后运行，由 grader 读入测试数据、调用选手函数并输出结果。

**题目侧要准备什么**（全部放在 `data/testdata/<题号>/`）：

1. `grader.cpp`：自带 `main()`，读入 `N.in`、调用选手函数、把结果写到标准输出（或自判后用退出码 0 / 非 0 表示 AC / WA）；
2. 头文件 `problem.h`（可多个，如 `problem.h` + `impl.h`）：写清选手要实现哪些函数；
3. 逐测试点数据 `N.in` / `N.out`：`.out` 是 grader 标准输出的期望值（留空则只按 grader 退出码判定）；
4. 需要的话照常勾选 SPJ：此时 `checker <in> <ouf> <ans>` 里的 `ouf` 就是 grader 的标准输出。

**选手侧怎么写**：`#include "problem.h"`，只实现头文件声明的函数，**不要自带 `main()`**（会与 grader 冲突导致 Compile Error）；只支持 C / C++ 提交，不需要读入也不应输出。

**现成示例**：题库 **#39「通信题：数组区间最大值（RMQ）」**（历史命名，实际是函数式交互题；grader 输出与 `N.out` 比对，可直接复制为模板）、**#5「函数式交互测试题（不许偷看）」**、**#25「函数式交互：数组第 k 小」**（留空 `.out`、按 grader 退出码判定）。

### 15. 通信题（两个选手程序合作）

> **这是与「交互题 · IO」「交互题 · 函数式」并列的第三种题型**，存库值 `problem_type = 'communication'`，独立实现（`src/communication.js` + `src/judge.js` 的通信题分支），不复用也不改变前两种交互题的语义。

**定义**：通信题需要**两个选手程序**进行通信、合作完成某项任务。

- **程序一**：接收问题的输入（题目数据里的 `N.in`）并产生某些输出；
- **程序二**：它的输入与程序一的输出相关（有时**原封不动**作为一个参数，有时由评测端**处理**后得到），它需要产生问题的解。

例子：UOJ #178 新年的贺电、UOJ #454【UER #8】打雪仗。

**两种连接方式**（题目侧在 `data/testdata/<题号>/meta.json` 里配置，键名 `pipe_mode`；后台编辑页「测试数据」卡片有下拉框，随「保存测试数据」一起保存）：

| 连接方式 | 流程 | 说明 |
| --- | --- | --- |
| **`relay`（评测端中转，默认）** | ① 用 `N.in` 跑**程序一**，收下它的 stdout；② 若题目提供 `grader.cpp`（评测端中转程序），以程序一的输出为 stdin 运行它，把它的 stdout 作为程序二的输入；③ 以（①或②的）结果作为 stdin 跑**程序二**，比较程序二的 stdout 与 `N.out`（或交给 checker） | 完全顺序、可复现、可逐点采样；**两个程序各自**受该测试点的时限 / 内存约束 |
| **`direct`（双向管道直连）** | 把程序一的 stdout 直接接到程序二的 stdin，两者**并行运行、边跑边传**；`duplex: true` 时再把程序二的 stdout 回传给程序一的 stdin | 适合「边跑边传 / 双向对话」式合作；不执行 `grader.cpp`；由于两个程序并行且评测端无法判断「空闲」，其超时闸门含 5 秒冷启动宽限（与 IO 交互题同一思路），**内存采样只覆盖程序二**（评测机只有一个内存采样通道） |

> 本地测试的常见形式（与上面两种连接方式对应）：手工输入 → 写辅助程序把第一个的输出转成第二个的输入 → **用双向管道把两个程序的标准输入输出连接起来**，见下面的「本地测试三种方式」。

**题目侧要准备哪些文件**（都在 `data/testdata/<题号>/`）：

1. **逐测试点数据 `N.in` / `N.out`**（必须，3~5 个就够）：`.in` 是交给**程序一**的题目输入；`.out` 是**程序二**输出应等于的标准答案，**留空**则只按程序二退出码判 AC（与函数式交互题同一口径）；`.out` + 勾选 SPJ 时交给 `checker`；
2. **`grader.cpp`（可选，评测端中转程序）**：自带 `main()`，评测机以 `grader < 程序一输出文件 > 程序二输入文件` 的方式运行它（即 **stdin → stdout 的过滤器**）：读取程序一的输出、按需处理后写成程序二的输入。退出码 `0` = 处理成功；**非 0 = 程序一的输出未通过校验**（判 WA，并把它的 stderr / stdout 结论回传到提交详情）。它属于受信任的评测设施：不计入选手时限 / 内存，不降权运行；留空 = 不中转，程序一的 stdout 原封不动作为程序二的 stdin。**程序一侧的通信量上限（`prog1_output_limit_bytes`）与它无关**，始终生效；
3. **`checker.cpp`（可选，Special Judge）**：勾选页面顶部「使用 Special Judge（SPJ）」后编辑 / 上传；判定时 `ouf`（选手输出）= **程序二**的标准输出，`in` = `N.in`，`ans` = `N.out`，**支持部分分**（`quitp`）；
4. **`meta.json` 里的三个开关**（后台「测试数据」卡片直接编辑，也可手改）：
   - `pipe_mode`：`"relay"`（默认）/ `"direct"`；
   - `prog1_output_limit_bytes`：**程序一输出（= 通信量）字节上限**，`0` = 不限；超出即 **WA 并给出「通信量超限」原因**（程序一写得太快时由跑完后的文件大小复核，写得多时被看门狗及时结束）；
   - `duplex`：仅 `direct` 有效，把程序二的输出回传给程序一的 stdin。

**选手侧怎么交（两个程序）**：题目页提交卡片会显示**两个代码框**——「程序一」与「程序二」，两者**共用同一个语言**（通信题仅支持 C / C++：评测时两个程序分别编译成两个独立可执行文件后对接运行）。**两个都必须填**，任一为空 / 编译失败都会给出明确的提示；提交记录列表里这类提交会带「两程序」标签，提交详情同时展示两段代码（各有「复制」按钮）与两个程序各自的判定消息。**不支持**「提交代码文件」这种单文件方式。

**时限 / 内存如何生效**：

- `relay`（默认）：**两个程序各自**受「该测试点点级限额 ?? 题目级限额」约束——程序一超时 / 超内存 → TLE / MLE（消息注明「程序一」），程序二同理（消息注明「程序二」）；判定用时取两者中较慢的一个，内存取两者峰值；
- 判定顺序：编译失败 → **Compile Error**（回传 g++ 原文并注明是「程序一」还是「程序二」）→ 运行崩溃 / 非 0 退出 → **Runtime Error** → 超时 **TLE** → 超内存 **MLE** → 程序一通信量超限 → **WA（通信量超限）** → 答案不符 → **WA**（`spj=1` 时由 checker 判分，支持部分分）；
- `direct`：两个程序并行，各自有独立闸门；超时判 TLE（消息说明是哪一个程序），内存只采样程序二（`memory_note` 字段会说明这一点）。

**本地测试三种方式**（用演示题 #40 的两个程序试最直观）：

1. **手工输入**：把题目输入写进文件 `in.txt`，分别运行两个程序，人工把第一个的输出贴给第二个：
   ```bash
   ./prog1 < 1.in > mid.txt      # 程序一：读题目输入，产生中间输出
   cat mid.txt                    # 看一眼程序一到底输出了什么
   ./prog2 < mid.txt              # 程序二：读中间输出，产生最终答案
   ```
2. **写辅助程序把第一个的输出转成第二个的输入**（等价于题目侧的 `grader.cpp`，用来验证「评测端处理」这一步）：
   ```bash
   ./prog1 < 1.in | ./grader | ./prog2      # grader 就是那个「stdin → stdout 的过滤器」
   ```
3. **用双向管道把两个程序的标准输入输出连接起来**（等价于 `direct` 模式，最接近真实评测）：
   ```bash
   # POSIX：mkfifo 造两条命名管道，交叉接线后把题目输入喂给程序一
   mkfifo p1 p2
   ./prog2 < p1 > p2 &
   ./prog1 < 1.in > p1 < p2 &     # 程序一：stdin 接 p2（程序二的输出，如需回传）
   wait
   # Windows / 跨平台：用一段 Node 脚本串两个程序（与评测端 direct 模式同一思路）
   node -e "const{spawn}=require('child_process'),fs=require('fs');const a=spawn('./prog1'),b=spawn('./prog2');a.stdout.pipe(b.stdin);b.stdout.pipe(process.stdout);fs.createReadStream('1.in').pipe(a.stdin);"
   ```
   两种写法都是「程序一的 stdout → 程序二的 stdin」，`direct` 模式下评测端做的就是这件事（并额外统计通信量、限制时限 / 内存）。

**现成示例**：题库 **#40「通信题演示：两程序合作求最大子段和」**（`relay` + 通信量上限 64KB，第 5 个测试点带点级限额 1000ms / 64MB，可直接复制为模板；题面、通信说明与后台配置都能看到完整做法）；`interactive_func` 的例题见 **#39「通信题：数组区间最大值（RMQ）」**（历史命名，实际是函数式交互题）、**#5**、**#25**。

## 三、管理员：其他后台功能

> 入口：侧边栏「管理后台」，按权限位展示模块；页面右上角均有「使用说明」按钮。

### 1. 题目重判

> 仅**超级管理员**可见（管理后台 → 题目重判）。

- 支持三种范围：**比赛某题**全部提交、**某题全部**提交（可区分普通提交与比赛提交）、**自定义提交 ID 区间**；
- 执行前先**预览命中数量**，确认后再执行；执行过程显示队列进度；
- 适用场景：修改测试数据、修正 SPJ、调整限制后重新判定历史提交。

### 2. 用户管理

- **列表与搜索**：分页展示用户，可按用户名 / 昵称 / UID 搜索；
- **编辑资料**：修改昵称、邮箱、简介，可**重置密码**（内置 admin 账号不可修改）；
- **权限配置**：为每个用户勾选 8 项权限位：
  - 审核类权限（题解审核 / 专栏审核）只能审核；
  - 管理类（题解管理 / 专栏管理）可审核且可编辑、删除；
  - 题目管理 / 用户管理 / 比赛管理 / 讨论管理为独立权限位；
  - **勾选全部 8 项即超级管理员**；
- **封禁（棕名）**：设置封禁时长（如抄题解、比赛作弊），期间限制发言 / 提交题解 / 编辑专栏，到期自动解除；
- 所有权限与处罚操作写入**社区管理记录**并通知被操作用户；**编辑用户资料（用户名 / 昵称 / 邮箱 / 简介 / 重置密码）属于日常维护，不计入社区管理记录**，社区管理页面不会出现此类条目。

### 3. 批量生成用户

> 入口：**系统设置 → 批量生成用户**（仅 admin）。

- 按「**前缀 + 编号（可按位数补零） + 后缀**」批量创建用户，例如前缀 `stu`、后缀 `test`、编号 1–3、位数 3 → `stu001test`、`stu002test`、`stu003test`；
- 可设置**起始 / 结束编号**、**编号位数**、**默认密码**、**邮箱域名**（自动生成 `用户名@域名`）；
- 已存在的用户名自动**跳过**；单次最多 **500** 个；
- 生成后展示账号表格，可**一键复制**（用户名 + 密码）或**导出 .txt**（含邮箱列），便于批量发放。

### 4. 比赛管理

- **新建比赛**：标题、类型（ACM / IOI / OI）、起止时间、Rated 与等级分阈值、是否公开；**所有比赛固定需要报名**，私有题目仅报名用户可见；
- **题目编排**：在比赛详情页添加题目并设置顺序与分值，赛后可调整；
- **榜单**：比赛进行中实时查看（每页 30 名）；OI 赛制赛中隐藏成绩、赛后自动公布；
- **Rating 结算**：Rated 比赛结束后点「结算 Rating」（需比赛管理权限），按 Codeforces 风格期望排名算法计算；参赛不足 2 人时标记跳过；
- 可对作弊用户执行「棕名·作弊」处罚（该场判 -1 分）。

### 5. 题解 / 专栏管理

- 后台菜单里是**两个独立页面**：**题解管理**（`#/admin/editorials`）只管题解，**专栏管理**（`#/admin/articles`）只管普通专栏文章 —— 两边列表、筛选、计数与分页**互不混入**（专栏管理在服务端排除了分类「题解」的文章，题解只出现在题解管理页）；
- **待审核列表**：用户提交的题解（题解管理页）/ 专栏文章（专栏管理页），可查看全文；
- **通过**：文章公开可见；**驳回**：填写原因，作者收到通知后可修改重交；
- 审核权限只能审核；管理权限还可**编辑、删除**任何文章；
- 分类（未分类 / 题解 / 科技·工程 / 算法·理论 / 生活·游记 / 学习·文化课 / 休闲·娱乐）由作者选择，审核时可调整；**专栏管理页的分类筛选不含「题解」**（它属于题解管理页）。

### 6. 讨论管理

- 查看全部讨论（含学术版 / 灌水区 / 站务版 / 题目讨论）；
- 支持**置顶 / 取消置顶**、**删除**、**关闭回复**；
- 操作写入社区管理记录并通知作者；用户举报在「反馈审核」中查看。

### 7. 反馈审核

- 用户提交的 **Bug / 建议 / 举报 / 投稿** 集中在此（仅 admin 账号可见入口）；
- 可**回复用户**（回复会通知用户）并在处理后**关闭**；
- 举报类反馈可按规则对违规用户执行封禁（见「用户管理」）。

| **清理多余数据** | 打开「清理多余数据」（入口在「系统设置」里的同名按钮，地址 `#/settings/cleanup`，仅 admin；旧地址 `#/admin/cleanup` 会自动跳转到这里）：9 类**缓存 / 临时 / 孤儿 / 过期**数据（判题临时目录、无题目引用的 SPJ 与交互器缓存、过期会话 / 待验证注册 / 登录失败计数、孤儿测试数据目录、孤儿头像、过大日志截断），每项先给数量与占用空间，可单独清理或一键全部清理；**用户、题目、比赛、提交、题解、讨论等内容数据一律不删**，结果逐项给出删除条数 / 释放空间 / 失败项并写入审计 |
| **批量生成用户** | 见前文 |
| **危险操作** | 打开「批量删除 / 重置页面」（仅 admin），见第四节 |

### 9. 板块与分类管理（仅超级管理员）

> 入口：板块管理是 **管理后台 → 讨论管理**（`#/admin/discussions`）下的**子页面** `#/admin/discussions/boards`；文章分类管理是 **管理后台 → 专栏管理**（`#/admin/articles`）下的**子页面** `#/admin/articles/categories`。两个父页面都是**大标题在最上面、子标签紧随其下**（「帖子管理 | 板块管理」「文章审核 | 分类管理」），点一下即可切换，地址可直接收藏 / 分享 / 刷新。两个子页面都**只对超级管理员显示入口**；其它管理员可以正常使用两个父页面，但看不到子标签，直接访问子页面地址会被友好提示并送回父页面列表（接口对非超管一律 403）。旧地址 `#/admin/taxonomy`（以及 `#/admin/discussions?taxo=board`）仍然可用，会自动跳到板块管理子页面。

- **两张可编辑表**：讨论区**板块**（默认：学术版 / 灌水区 / 站务版 / 题目总版，key = `academic` / `water` / `site` / `problem`）与专栏**文章分类**（默认：未分类 / 题解 / 科技·工程 / 算法·理论 / 生活·游记 / 学习·文化课 / 休闲·娱乐，key = `uncategorized` / `solution` / `tech` / `algorithm` / `life` / `study` / `entertainment`）。
- **内部 key 与显示名分离**：key 是内容的真实归属（讨论的 `board`、文章的 `category` 存的就是它），且**一律是英文 / 数字 slug**；显示名可以是任意中文。**重命名只改显示名、key 永远不变**，因此已有讨论 / 文章不会失联；讨论页板块下拉与筛选条、文章页分类标签与筛选、编辑器下拉、后台审核页筛选全部改为读接口，改名后各处显示同步更新（历史内容若引用了已不在表里的值，会原样显示原值，不会空白或 undefined）。
- **新建**：填显示名即可（key 可留空自动生成，也可自己指定英文 / 数字 slug），顺序留空则排到最后。
- **删除保护**：板块下仍有讨论、分类下仍有文章时**默认拒绝删除并给出条数**；界面会弹出「选择迁移目标」对话框，选定后**批量迁移 + 删除在同一事务内完成**（任一步失败整体回滚）。系统内置项（表格里带「系统」标记）删除时也必须显式指定迁移目标。
- **系统项**：板块「学术版」（key `academic`）是未指定板块时的兜底板块，**不可删除**（可改名）；分类「题解」（key `solution`）被题解流程使用（关联题目的文章必须是它），**不可删除也不可改名**，表格中标注为「系统 / 不可删除」。
- 每次新建 / 改名 / 删除都写审计，动作名为 `board_create` / `board_rename` / `board_delete` / `category_create` / `category_rename` / `category_delete`，可在「社区管理」查看。

### 10. 版本更新

> 入口：**系统设置 → 版本更新**（仅内置 `admin` 账号）。

- 区块内显示**当前版本**、**官方最新版本**、**最后检查时间**、**实际使用的更新源**与**服务启动方式**；
- 点击「**重新检查**」可强制刷新版本信息（按钮会立即显示「正在检查…」，检查完成后展示结果）；更新源异常时会逐条列出每个源的失败原因；
- 勾选「**更新前备份数据库**」（默认勾选）→ 点「**立即更新到 vX.Y.Z**」→ 页面实时显示进度：检查最新版本 → 备份数据库 → 下载新版本代码 → 覆盖代码文件 → 重启服务；
- 更新只覆盖**程序代码**：数据库、题库测试数据、附件、头像与本地配置（`deploy/panel.env`）均不受影响；
- 若当前进程没有重启服务的权限（systemd 部署以普通用户运行时常见），界面会提示**手动执行** `sudo systemctl restart lczoj`（此时代码已更新完成）；如需今后自动重启，在服务器上执行一次 `sudo bash deploy/grant-restart-permission.sh`；
- 命令行方式与完整说明见 [UPDATE.md](UPDATE.md)。

## 四、删除数据与批量删除 / 重置（重要）

> 删除操作**不可恢复**，请先确认或做好备份（备份方法见 [DEPLOYMENT.md](DEPLOYMENT.md) 第七节）。

### 1. 单个删除

| 对象 | 删除方式 |
| --- | --- |
| 题目 | 题目管理行内「删除」或编辑页顶部删除；该题的提交、收藏、关联题解与讨论一并清理 |
| 文章 / 题解 | 作者在「个人中心 → 专栏」删除；管理员在题解 / 专栏管理中删除任意文章 |
| 讨论 / 回复 | 作者可删除自己的内容；管理员在讨论管理中删除 |
| 比赛 | 比赛管理列表中删除 |
| 用户 | 用户管理或批量删除页面（内置 admin 不可删除） |

### 2. 批量删除 / 重置页面

> 入口：**系统设置 → 危险操作 → 打开批量删除 / 重置页面**（仅 admin）。

- **按类型批量删除**：
  - 类型可选：文章（题解 / 专栏）、反馈 / 投稿 / 举报、题目、比赛、讨论、用户；
  - 输入 ID 列表（**逗号分隔，支持范围**，如 `1,3,5-8` 表示删除 1、3、5、6、7、8）；
  - 执行后**同时清理关联数据**（提交、回复、收藏等）。
- **删除用户**（独立卡片）：按用户名 / 昵称 / 邮箱搜索后逐个删除；删除会清理其提交、回复、收藏等全部关联数据；内置 admin 账号受系统保护不可删除。
- **清空网站到初始状态**：删除全部题目 / 文章 / 反馈 / 比赛 / 讨论 / 提交 / 普通用户，**仅保留 admin 账号与系统设置**（需二次确认）。

### 3. 编号释放说明

- 题目、比赛、题解、讨论等**内容表的编号在删除后会被释放**：删除编号最大的内容后，新建内容会**复用该编号**（例如删除 3 号题后，新建题目会再次获得编号 3）；
- 提交记录、通知等流水记录仍按自增顺序编号，不会复用。

### 4. 恢复网站到默认状态（重置数据）

> 该操作会**清空全部数据**（数据库、题库测试数据、附件、头像、判题缓存），程序代码与配置不受影响；清空后首次启动会自动重建管理员与 5 道内置演示题。

**快捷入口**（两个平台行为完全一致，底层都是 `deploy/reset.js`）：

| 平台 | 命令 |
| --- | --- |
| Windows | 双击 `reset.bat`，或在项目目录执行 `reset.bat --yes` |
| Linux / macOS | `./reset.sh`，或 `node deploy/reset.js` |

**常用参数**

| 参数 | 作用 |
| --- | --- |
| （无参数） | 停止服务并清空数据，执行前**询问确认** |
| `--yes` | 不询问，直接执行（脚本化场景；非交互终端下必须加） |
| `--check` | 只显示将要执行的操作，**不做任何修改**（建议先跑一次） |
| `--start` | 清空后**前台**启动（Ctrl+C 停止） |
| `--daemon` | 清空后**后台**启动（日志 `logs/lczoj.log`，进程号写入 `deploy/panel.pid`） |
| `--port 8080` | 指定端口（默认取 `PORT` 环境变量，否则 80） |
| `--all` | 连同命令行含 `server.js` 的其它疑似残留进程一并结束（默认不动，避免误杀同机其它实例） |
| `--clear-logs` | 同时清空 `logs/` 下的日志文件 |

**执行流程**：① 按 **systemd 服务 → PM2 应用 → `deploy/panel.pid` → 端口监听进程** 的顺序停止服务，并确认端口已释放；② 删除数据目录（默认 `<项目目录>/data`，可用 `OJ_DATA_DIR` 指定；Windows 上若文件句柄尚未释放会自动退避重试）；③ 按需重新启动并等待 `/api/health` 就绪，最后打印访问地址。

**注意事项**

- 服务由 **systemd** 托管时，脚本会执行 `systemctl stop lczoj`（否则 `Restart=always` 会立刻把服务拉起、数据目录被重新创建导致「重置无效」）；没有权限时会提示执行 `sudo systemctl stop lczoj`；
- 服务由 **PM2** 托管时执行 `pm2 stop lczoj`，清空后可用 `pm2 restart lczoj` 恢复；
- 由面板（宝塔 Node 项目 / 小皮计划任务）托管时，请先在面板中停止该项目再执行本脚本；
- 删除失败时脚本会列出被占用的文件，并以非 0 退出码结束（不会静默跳过）。

## 五、常见使用问题速查

| 现象 | 处理 |
| --- | --- |
| 提交后长时间「等待评测 / 评测中」 | 查看服务端日志；确认该语言的编译器已安装（「系统设置」（`#/settings`） → 评测设置，或执行 `node deploy/check-env.js`） |
| 语言下拉里某语言显示「未安装」 | 该语言的工具链未安装，安装后刷新页面即可（安装命令见 [LANGUAGES.md](LANGUAGES.md)） |
| 普通题目里找不到「提交答案」 | 属于正常行为：「提交答案」只对**提交答案题**显示；如需改为提交答案题，在题目编辑器的「题目类型」里选「**提交答案**」 |
| 上传答案 ZIP 提示请求体过大 / 413 | 前置 Nginx 需配置 `client_max_body_size 64m;` |
| 数学公式显示为源代码 | 浏览器无法访问 CDN，系统自动回退到内置渲染器（效果略有差异但可用） |
| 编辑页测试数据显示「数据过大」 | 单个文件超过 16 KB 不预览，属正常行为，保存与评测都使用完整数据 |
| SPJ 题上传数据包被拒绝 | 数据包内必须包含 `checker.cpp` |
| 交互题所有测试点提示缺少 `interactor.cpp` / `grader.cpp` | 只选了题目类型但没保存配套源码：在「交互题配置」里粘贴 / 上传后点「保存题目信息」（详见 [INTERACTIVE.md](INTERACTIVE.md)） |
| 交互题报「判题失败」 | 多为交互器自身问题：退出码非约定值、数据文件读不到、用了 testlib 却没在第一行调用 register 函数（改用 `registerInteraction(argc, argv);` 或加 `disableFinalizeGuard();`） |
| 交互题开 SPJ 后全 WA / 判题失败 | 检查交互器是否把选手最终答案写入 `argv[2]`（不开 SPJ 时不需要写），以及 checker 是否按 in / ouf / ans 正确读取（详见 [INTERACTIVE.md](INTERACTIVE.md)） |
| 导入题目后出现重复题目 | 导入时「同名题目」策略选成了「允许重复」；改为「跳过」或「覆盖」后重新导入 |
| 页面样式与旧版不一致 | 浏览器缓存，强制刷新（`Ctrl+F5`） |
| 忘记管理员密码 | 见 [FAQ.md](FAQ.md)（可删除 `data` 目录重建，或由维护者重置） |
